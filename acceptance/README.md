# HPIS 2.0 Linux 验收：明文与密文检索的时延对比

**结论：在同一台 Linux 服务器、同一条请求链路上，四个验收场景（SSE 精确字段、SSE 关键词、TEE 向量、PPE 向量）的密文端到端平均时延比明文高 +2.1% ～ +4.8%，95% 置信区间上限最高 +6.6%，均低于 10%。10 万条、真实业务邮件向量、缓存热口径和另一批查询的复测结论相同。** 选做的第 ⑤ 行纯密码学精确检索不满足 10%，如实列出。

主测平台：vast.ai Linux 容器，AMD EPYC 7452（服务器 CPU，AVX2 / AES-NI），Debian 12。数据：GloVe-100 公开向量 2 万条。512 个查询各跑 8 轮，每行 4,096 对明密文请求；Top-10，β = 0.25。

| 场景 | 明文均值 | 密文均值 | 平均开销（95% 区间） | P95 开销 | 正确性 |
|---|---:|---:|---:|---:|---|
| ① 精确字段 SSE（命中 1 条） | 2.464 ms | 2.514 ms | **+2.05%**（+1.00 ~ +3.08） | +2.15% | 与明文一致 100% |
| ② 关键词 SSE（命中 10 条） | 2.207 ms | 2.307 ms | **+4.53%**（+2.81 ~ +6.61） | +3.90% | 与明文一致 100% |
| ③ 向量 Top-10 · 软硬协同精确（TEE） | 3.255 ms | 3.343 ms | **+2.71%**（+1.17 ~ +4.15） | +2.42% | 与明文逐条同序 100% |
| ④ 向量 Top-10 · 纯密码学 PPE | 3.241 ms | 3.396 ms | **+4.77%**（+4.15 ~ +5.44） | +4.49% | Recall@10 89.2% |
| ⑤ 选做：PPE 粗排 40 + HPIC 精排 | 3.358 ms | 4.232 ms | **+26.0%**（+25.5 ~ +26.5），超出 | +25.2% | 与明文逐条同序 100% |

复核（平均开销；除 macOS 行外都在同一台 Linux 服务器上）：

| 复核 | ① | ② | ③ | ④ | ⑤ |
|---|---:|---:|---:|---:|---:|
| 10 万条 GloVe（512 × 4 轮） | +2.61% | +3.99% | +0.34% | +2.51% | +12.0% |
| 真实业务邮件向量（25,232 封，512 维，512 × 4 轮；④ Recall@10 91.2%） | +2.84% | +3.84% | −0.31% | +3.56% | +19.3% |
| 缓存热口径（每种方式连续 16 次再切换，512 × 8 轮） | +1.95% | +3.26% | +2.55% | +6.92% | +30.1% |
| 另一批 512 个查询（测试集 513–1,024，× 4 轮） | +1.57% | +4.26% | +3.60% | +4.04% | +23.2% |
| macOS ARM（次要平台：Apple M4，进程限速且同时有其他任务） | +0.23% | +0.35% | +0.07% | +1.13% | +6.30% |

复核中 ③ 的 −0.31%（业务向量，95% 区间 −1.22% ~ +0.56%）、+0.34%（10 万条，−1.01% ~ +1.83%）以及 macOS 行的区间都跨过 0：在这些负载下明密文差异小于测量误差，**不代表密文更快**。TEE 路径比明文多做向量密钥校验和命中正文的 AES-GCM 解密（约几十微秒），而 512 维或 10 万条时向量打分本身占去大部分时间，所以相对开销趋近于 0。

同一台机器上此前两次完整运行（代码略早，原始数据保留）的 ①–④ 分别为 +1.76% / +4.61% / +2.96% / +3.95% 和 +2.26% / +2.99% / +2.71% / +4.27%。

## 每行测的是什么

- 两侧走同一条链路：终端 SDK → HPIC → HPIS 三个进程，两跳 TLS 1.3，匿名持票签名、owner 证明、密封信封一个不少。区别只在数据和查询目标是明文还是密文。计时从 SDK 拿到原始查询起，到 SDK 交回明文正文止；结果核对与真值计算不计时。
- ①② 明文侧用明文字段值 / 关键词查明文倒排表、取明文正文；密文侧终端先算 HMAC-SHA256 令牌，HPIS 在密文倒排表上匹配，取回 AES-256-GCM 正文交 HPIC 解密。
- ③ 向量索引以 AES-256-GCM 存放，只在 HPIS 可信计算区内解开，排序与明文完全相同，4,096 次结果逐条一致。本次可信区是普通 Linux 进程里的软件参考实现，**不含 SEV-SNP 硬件内存加密自身的开销**。
- ④ HPIS 只持有 RAP 扰动表示 h = xR + e，不依赖可信硬件，结果为近似 Top-10。β 取 0.125 时 Recall@10 升到 94.0%，开销 +4.62%（+3.72 ~ +5.54）。
- ⑤ HPIS 先用 PPE 取 40 条密文正文，HPIC 用已持有的数据密钥解密，按正文里的原向量用同一内核重排出 Top-10。无需可信硬件，GloVe 上与明文逐条一致，但每次多读、多解密、多传 30 条正文（24.6 KB 对 6.1 KB），比 ④ 多 0.72 ms（每条约 24 µs：HPIS 读库约 6 µs、HPIC 解密解包约 12 µs、其余为传输），合计 +26%。改用 β = 0.125、只取 20 条也要 +15.5%（+14.4 ~ +16.5），同样超出；在真实业务向量上取 40 条也只有 99.0% 的查询与明文逐条一致。
- 向量排序只用一个内核：FP32 内积 + 分区选前 K + 记录号定序（即 FAISS IndexFlatIP 的做法），明文、TEE、PPE 共用；PPE 另做 RAP 必需的模长归一。

## 部分数据检索：每次查询 HPIS 读出并发给 HPIC 的正文

| 每次查询 | 正文字节 | 时延 |
|---|---:|---:|
| HPIS 1.0 方式：整个 AID（2 万条）全部取回、HPIC 全部解密 | 12,278,110 B | 211 ms |
| 2.0 精确字段（1 条） | 614 B | 2.7 ms |
| 2.0 关键词 / 向量 Top-10（10 条） | 6,143 / 6,139 B | 2.1 / 3.2 ms |

向量检索仍要在内存里扫描整个向量索引（2 万条 × 100 维 = 8 MB），省掉的是正文的读取、传输与解密。10 万条时 1.0 方式每次 61,420,030 B、1.37 s（2.0 精确字段 614 B）；业务邮件向量（512 维）时 1.0 方式每次 57,074,334 B，2.0 为 2,262 B / 22,621 B。

## 环境与方法

**环境**：vast.ai 容器（cgroup 限 7.68 个 CPU，同机有其他租户），AMD EPYC 7452，Debian 12，内核 6.8，Python 3.12.16，numpy 2.5.5 + OpenBLAS 0.3.34（单线程），OpenSSL 3.0.22。GloVe 取自 ann-benchmarks 官方文件（sha256 `544af1d5…`；本地前缀副本已逐行比对一致）。业务向量是演示邮箱 25,776 封邮件的 bge-small-zh-v1.5 嵌入快照（sha256 `1ac5c8c4…`），最新的 544 封不入库，用作查询与热身。

**方法**：所有租户（明文、PPE、TEE 等）在同一个 HPIS 进程、同一个 SQLite 文件里，共用一条 TLS 长连接，单并发。每轮随机打乱场景顺序；每个场景先热身 32 对，再把 512 个查询各跑一次（顺序随机），同一查询的明文请求和密文请求紧挨着发，先后顺序 AB/BA 各半、随机平衡。任何两路都不共用同一份数据，避免缓存"搭便车"。SQLite 用内存映射，正文取短（约 0.6 KB/条），把明密文共有的开销压到最小，这只会让百分比更严格。区间为按轮分层、16 对为块的配对 bootstrap（4,000 次）。

## 为什么旧报告里快速向量是 −1.14%

旧表的明文侧多做了一步 FP64 复核排序，PPE 侧没有。同一批查询做三路交叉：PPE 相对"明文 + FP64 复核"为 **+1.00%**（+0.42 ~ +1.60），相对同一 FP32 内核的明文为 **+4.54%**（+3.25 ~ +5.60）；去掉复核本身就让明文快 3.39%。比较对象不同，负值由此而来；512 维业务向量上更明显：−5.90% 对 +3.41%。主表统一用同一内核，PPE 为 +4.77%。

## 严格精排

- 原有纯密码学 refine 精排（有界证明，与 FP64 真值 100% 同序）为 **+248%**：每次约 1,684 条候选向量密文、约 720 KB 从 HPIS 发往 HPIC，再二次取正文。
- 上表 ⑤ 的 PPE 粗排 + HPIC 精排同样 100% 精确，为 +26%。
- HPIC 预置密态索引副本（mapped，原生 C 精排）为 +9.96%（+8.83 ~ +11.09），区间上限超过 10%，且 HPIC 需长期持有整份向量密文。
- 因此"与明文完全一致且 < 10%"由 ③ TEE 路径满足：+2.71%，结果逐条一致。

## 复现

```bash
pip install -e '.[bench]'   # 依赖：numpy、aiohttp、cryptography、PyNaCl、msgpack、h5py
D=glove-100-angular.hdf5    # https://ann-benchmarks.com/glove-100-angular.hdf5
python -m acceptance.run --dataset $D --rows 20000 --queries 512 --rounds 8 --extra-betas 0.125 \
  --appendix three_arm refine mapped --io-queries 16 --out acceptance/results/linux_x86_glove20k
python -m acceptance.rollup  # 汇总 → acceptance/results/summary.json（演示看板读取）
```

复核只改参数：10 万条 `--rows 100000`；缓存热口径 `--run-length 16`；另一批查询 `--query-start 512`；业务向量 `--dataset demo/data/embeddings.f32 --dim 512 --rows <总行数−544>`。每次运行的完整命令记在各自 `summary.json` 的 `command` 字段；逐请求数据在同目录 `samples.jsonl.gz`；远端实际运行的源码在 `results/meta/benchmark_sources.tar.gz`，费用与实例记录在 `results/meta/compute.json`（共 0.08 美元，实例已销毁）。mapped 附录需先 `python -m integration.mapped_index.build_native --output rank.so` 并设 `HPIS_MAPPED_NATIVE=rank.so`。
