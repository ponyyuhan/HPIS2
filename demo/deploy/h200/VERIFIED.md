# 验证记录（2026-11-20）

测试使用演示程序自己的客户端 `demo/llm.py` 和提示词 `demo/prompts.py`，两个模型用同一份提示词。题目是 `fixtures.json` 里的 4 个中文问题，邮件均为虚构：项目改期（同时问目标、交付时间和未解决问题）、单一事实追问、信用卡账单（含交易明细 CSV 和后续退款）、出差安排（酒店地址邮件中未提及）。请求逐个串行发出，temperature 为 0.2，max_tokens 为 600。判分规则：关键事实全部正确且没有混入干扰邮件，记为“正确”；引用编号都在证据范围内，必引的邮件已引用，且未引用干扰邮件，记为“引用符合预期”。原始数据（含每次的完整回答）在 `results/`。

## 思考是否关闭（OpenRouter，单次请求）

| 模型 | 不传 reasoning | `reasoning.effort = "none"`（默认） | `reasoning.enabled = false` |
|---|---|---|---|
| `qwen/qwen3.6-27b` | 默认开启思考：生成 965 字思考，300 token 用尽，没有给出回答 | 推理 token 为 0 | 推理 token 为 0 |
| `qwen/qwen3.8-27b` | 先产生 51 个推理 token | 推理 token 为 0 | 推理 token 为 0 |
| `google/gemma-4-31b-it` | 推理 token 为 0（默认不思考） | 推理 token 为 0 | 推理 token 为 0 |

下表所有正式测试中，`usage.completion_tokens_details.reasoning_tokens` 均为 0，流中也没有出现 reasoning 字段。

## 正式结果：交付默认配置（每个模型 4 题 × 5 次）

OpenRouter 路由设为 `provider.sort = "throughput"`，并排除 fp4 量化的服务商。

| 模型 | 服务商 | 正确 | 引用符合预期 | 推理 token | 首字延迟 p50 / p90 / max (ms) | 总耗时 p50 (ms) | 解码 tok/s p50 | 平均输入 / 输出 token |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| `qwen/qwen3.6-27b` | Reka | 20/20 | 20/20 | 0 | 518 / 621 / 649 | 1453 | 98 | 1010 / 95 |
| `qwen/qwen3.8-27b` | Cerebras, Wafer | 20/20 | 20/20 | 0 | 390 / 566 / 1622 | 427 | 1444 | 1010 / 86 |
| `google/gemma-4-31b-it` | Friendli | 20/20 | 20/20 | 0 | 294 / 514 / 819 | 559 | 357 | 1052 / 93 |

格式方面，每个模型在项目改期两题上的 10 次回答都写明了“原定 12 月 8 日，后改为 12 月 15 日”，多问题的那道题 5 次都使用了加粗标签。速度取决于 OpenRouter 背后服务商的硬件（例如 Cerebras），不代表 H200 上的表现。

## 路由对比（每个模型 4 题 × 5 次，全部正确）

| 模型 | OpenRouter 默认路由：首字延迟 p50 / p90 / max (ms)，tok/s | 按吞吐量排序（允许 fp4）：首字延迟 p50 / p90 / max (ms)，tok/s |
|---|---|---|
| `qwen/qwen3.6-27b` | 972 / 1839 / **8418**，39 | 522 / 619 / 677，91 |
| `qwen/qwen3.8-27b` | 500 / 848 / 1015，268 | 358 / 550 / 622，1726 |
| `google/gemma-4-31b-it` | 495 / 1091 / 1301，168 | 246 / 311 / 449，304（ModelRun，fp4） |

默认路由会把请求分散到多个服务商，首字延迟的尾部可达 8.4 秒。改为按吞吐量排序后，这组测试的首字延迟全部低于 0.7 s。交付配置因此按吞吐量排序。为了更接近 H200 上的 BF16 质量，交付配置还排除了 fp4。这样 Gemma 改由 Friendli 提供服务，首字延迟 p50 从 246 ms 变为 294 ms，p90 从 311 ms 变为 514 ms。正式结果中最慢的一次首字延迟为 1.6 s（Qwen3.8）。

## 表格计算的稳定性（“最大一笔消费”）

提示词加入“需要比较或计算时，逐条核对证据中的原始数字”这条规则后，信用卡一题累计测试 27 次（含 `table-stress-*.json` 中每个模型额外跑的 10 次）。结果：Qwen3.6 有 26 次正确；Qwen3.8 和 Gemma 都是 27 次全对。Qwen3.6 唯一一次失误，是说“本期邮件未提及最大消费”，并引用了 10 月账单。加入这条规则之前的试跑中，Qwen3.6 曾把 2,199 元误认为最大一笔。不开思考时，Qwen3.6 偶尔会在表格比较上出错。

## 其他检查

- 单元测试：`.venv-demo/bin/python -m unittest demo.tests.test_llm -v`，23 项全部通过，耗时约 3 s，不访问网络。测试用本地假服务器模拟 vLLM 和 OpenRouter 的流式输出，覆盖：拆开的 UTF-8 字符、注释行、没有空行分隔的事件、缺少 `[DONE]`、usage 放在最后一个 chunk、流中途报错、超时、HTTP 401/404、思考块泄漏、客户端中途断开等情况。
- `smoke.py` 在系统自带的 Python 3.9 下，对本地假 vLLM 跑通了以下情况：正常服务、服务端默认仍会思考（能检出）、模型名不存在、端口未开。
- `serve.sh` 在 macOS 自带的 bash 3.2 下用 `--print` 检查了 Docker、`--detach`、`--native`、本地权重目录和额外参数等组合。所有 vLLM 参数都已在 v0.34.0 和 v0.32.0 的源码中核对。
- 整套 OpenRouter 测试共 242 次请求，花费约 0.17 美元。
